# New-AuthentikApplication

## SYNOPSIS

Creates the seeded Authentik applications and the providers behind them

## SYNTAX

### __AllParameterSets

```
New-AuthentikApplication [[-ApplicationName] <string[]>] [-SkipProvider] [-PassThru] [-WhatIf]
 [-Confirm]
```

## DESCRIPTION

Creates nine applications from Data\AuthentikApplications.csv over every provider type the seed
can make: a proxy-provider intranet, a confidential OAuth2 client with a strict redirect URI, a
public client with a regex redirect, a payroll console the policies restrict, a SAML partner portal
whose responses are signed by a keypair the seed generates, an LDAP directory gateway and a RADIUS
network access provider that serve only through an outpost, a registered application with no
provider and no launch URL, and one hidden from the user library. Between them they cover the shapes
an application inventory or an access review has to handle.

An Authentik application is a thin object over a provider, and a provider needs an authorization
flow and an invalidation flow by primary key. The instance's default flows are looked up once per
session, so the CSV never has to know a UUID. The seed domain in the CSV URLs is replaced with the
connection's email domain, so one file serves any instance. Provider-specific settings ride in a
Settings cell of key=value pairs, with | separating the items of a list, and any URL among them is
substituted the same way. The SAML provider signs with a self-signed keypair named with the prefix,
generated by the instance on the first run and reused afterwards, so no real key ever signs a lab
assertion and teardown has something of its own to remove. The RADIUS shared secret is generated at
creation and never written to the CSV.

Every provider is created with the property mappings the admin UI would have selected for it: the
openid, email and profile scopes on an OAuth2 provider, those plus the proxy scope on a proxy
provider, and the standard UPN, name, email, username, user id and group attributes on a SAML
provider. The API attaches none by itself, and a provider without them issues tokens with no
claims and assertions with no attributes, which nothing can sign in through. The defaults are
found by their managed identifiers, so they resolve on any instance; one the instance lacks is
skipped with a verbose note.

Applications have no attributes, so the bracketed seed marker goes into the description. That, with
the slug prefix, is what teardown proves ownership by.

## EXAMPLES

### Example 1: Creates every seeded application with its provider

```powershell
New-AuthentikApplication
```

Output: None

Use case: Called by New-AuthentikEnvironment after the users step

### Example 2: Creates just the application the policies bind to

```powershell
New-AuthentikApplication -ApplicationName 'Payroll Console' -PassThru
```

Output: The application, with its provider's primary key and its pbm_uuid

Use case: Reproducing the policy-restricted case on its own

### Example 3: Lists the applications that would be created, none with a provider

```powershell
New-AuthentikApplication -SkipProvider -WhatIf
```

Output: One WhatIf line per application

Use case: Checking slugs against an instance before anything is created
